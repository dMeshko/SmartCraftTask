# SmartCraftTask — Warehouse & Stock API

A small .NET 10 service for managing warehouses and the stock lines they hold. REST API,
SQL Server persistence, run locally or entirely in Docker.

---

## Running it

### Everything in Docker

```bash
cp .env.example .env          # local SQL Server credentials, git-ignored
docker compose up -d --build
```

The API comes up on <http://localhost:8080>, with Swagger UI at
<http://localhost:8080/swagger>. The `smartcrafttask` service waits for the database's
healthcheck to pass before starting, so the first run is ordered correctly.

### Database in Docker, API from the IDE

```bash
cp .env.example .env                 # once, if you have not already
docker compose up -d sql-server      # SQL Server on localhost:6433
dotnet run --project SmartCraftTask --launch-profile http
```

The API is then on <http://localhost:5087>, Swagger UI at <http://localhost:5087/swagger>.
`appsettings.Development.json` already points at `127.0.0.1,6433` with the credentials from
`.env`, so no further configuration is needed.

On startup the service applies any outstanding EF Core migrations and, if the database is
empty, seeds three warehouses (one of them deactivated) and three stock lines.

The service speaks HTTP only. TLS is assumed to terminate at whatever sits in front of it, so
there is no in-app HTTPS redirection — with none configured it would log a warning on every
start and redirect nothing.

### Configuration

| Key | Where | Purpose |
| --- | --- | --- |
| `SQL_SA_PASSWORD` | `.env`, from `.env.example` | SA password for the SQL Server container |
| `SQL_DATABASE` | `.env`, from `.env.example` | Database name (`Calentra`) |
| `ConnectionString` | `appsettings*.json`, or env var | Read by the app; the compose file injects the container-network form |

### Tests

```bash
docker compose up -d sql-server      # required: the integration tests use it
dotnet test
```

29 tests, about two seconds. See [Testing](#testing) for what they cover and why they are
shaped this way.

### Exercising the API by hand

**Swagger UI** at `/swagger`, in Development only. The OpenAPI document itself is at
`/openapi/v1.json` and is generated by .NET 10's built-in `Microsoft.AspNetCore.OpenApi` — the
only thing Swashbuckle contributes here is the UI, via `Swashbuckle.AspNetCore.SwaggerUI`. The
project sets `GenerateDocumentationFile`, so the `///` summaries on the controllers and DTOs
become the endpoint and schema descriptions the UI displays; a document transformer supplies the
title and description.

`SmartCraftTask/SmartCraftTask.http` has a ready-made request per endpoint, runnable from
Rider or VS Code. The seeded warehouse ids are fixed (`1111...`, `2222...`, `3333...`) so the
requests work straight after a fresh start.

## The API

Stock lines are addressed through the warehouse that holds them, mirroring the fact that they
belong to it and cannot exist on their own.

| Verb | Route | Success | Other responses |
| --- | --- | --- | --- |
| `GET` | `/warehouse?isActive=` | `200` | — |
| `GET` | `/warehouse/{id}` | `200` | `404` |
| `POST` | `/warehouse` | `201` + `Location` | `400`, `409` duplicate code |
| `PUT` | `/warehouse/{id}` | `204` | `400`, `404` |
| `DELETE` | `/warehouse/{id}` | `204` | `404` |
| `GET` | `/warehouse/{id}/items?isOnStock=` | `200` | `404` unknown warehouse |
| `GET` | `/warehouse/{id}/items/{itemId}` | `200` | `404` |
| `POST` | `/warehouse/{id}/items` | `201` + `Location` | `400`, `404`, `409` duplicate SKU or deactivated warehouse |
| `PUT` | `/warehouse/{id}/items/{itemId}` | `204` | `400`, `404` |
| `DELETE` | `/warehouse/{id}/items/{itemId}` | `204` | `404` |

Every failure is RFC 9457 `application/problem+json`, including validation errors, which
arrive as a per-field `errors` dictionary.

`409` is used deliberately where a request is *well formed but conflicts with the world* — a
duplicate code or SKU, or stock added to a deactivated warehouse. `400` is reserved for
payloads that are wrong on their face. Keeping those apart means a client can tell "fix your
request" from "the state changed under you".

## Key decisions and trade-offs

### Warehouse is an aggregate root; Item belongs to it

`Item`'s mutators are `internal` and `Warehouse.Items` is an `IReadOnlyCollection`, so stock
lines can only be created, changed or removed through `Warehouse.AddItem`, `TryUpdateItem` and
`TryRemoveItem`. Two business rules live inside the root as a result:

- a SKU is unique within a warehouse (case-insensitively),
- a deactivated warehouse cannot take new stock.

I did not go further into DDD. There are no repositories (`DbContext` is already a unit of
work), no domain events, no separate domain project, and no CQRS. For a service this size those
would be ceremony; the aggregate boundary earns its place because it has real invariants to
protect, and because the API was already shaped that way.

**The trade-off is real:** every write to a stock line loads the whole aggregate
(`Include(w => w.Items)`) so the root can check its invariants. With thousands of lines per
warehouse that becomes expensive, and the honest answer would be to reconsider the boundary or
introduce a separate read model. Reads already sidestep it — they project straight to DTOs in
SQL and never materialise an entity.

### Validation at the edge, invariants in the domain

FluentValidation owns *shape*: required fields, lengths, the `^[A-Z0-9-]+$` code and SKU
format, numeric ranges. It runs in an action filter that renders failures through the same
`ProblemDetailsFactory` `[ApiController]` uses, so hand-written and framework validation are
indistinguishable to a client.

The domain owns rules that can only be judged with state loaded, and throws `DomainException`,
which an `IExceptionHandler` turns into a `409`. Genuine programming errors (a negative
quantity that validation should already have rejected) throw `ArgumentOutOfRangeException`
instead and surface as `500` — they are bugs, and should look like bugs.

Using exceptions for expected business outcomes is arguable. A `Result<T>` would avoid it at
the cost of plumbing through every call site; at this size I preferred the smaller code, and
would revisit if these paths became hot.

### Mapster maps outward, never into an aggregate

`Warehouse → WarehouseResponse` and `Item → ItemResponse` are Mapster's job, registered as
`IRegister` configs and applied as `ProjectToType` so the projection is translated into SQL
rather than done in memory. `WarehouseResponse.ItemCount` becomes a `COUNT(*)` subquery.

Nothing maps *into* a `Warehouse` or an `Item`: a mapper writing directly onto an entity would
walk straight past the invariants the aggregate exists to enforce. `AddressDto → Address` is the
one inbound mapping, and deliberately so — `Address` is a value object with no invariants
beyond its shape.

### EF Core with fluent configuration only

One `IEntityTypeConfiguration` per entity, picked up by `ApplyConfigurationsFromAssembly`; no
data annotations on entities and no mapping concerns leaking into the domain.

- **`Address` is a complex type**, not an owned entity: it flattens into `Street`, `PostalCode`,
  `City`, `Country` columns on `Warehouses` with no shadow key and no join, which is what a
  value object should compile down to.
- **`Item.IsOnStock` is a persisted computed column** —
  `CASE WHEN [Quantity] > 0 THEN 1 ELSE 0 END PERSISTED` — with a private setter so nothing in
  C# can assign it. Quantity is the single source of truth, the two cannot drift, and
  `?isOnStock=` is answered in SQL against an indexable column.
- **Composite unique index on `(WarehouseId, Sku)`** backs the aggregate's rule at the database
  level, so two concurrent creates cannot both slip through the in-memory check.
- **Ids are UUIDv7** (`Guid.CreateVersion7()`), generated by the aggregate. Sequential, so
  they do not fragment the clustered index the way random GUIDs do.

### Known limitations

- **No authentication or authorisation.** Next on the list; see below.
- **Migrations are applied at startup.** Convenient for a task, wrong for a deployment with
  more than one replica — two instances would race. It belongs in a deployment step or an
  init container.
- **Local credentials are only half tidy.** `.env` is git-ignored and shipped as
  `.env.example`, but the same throwaway password is still committed in
  `appsettings.Development.json` and in the test fixture's connection string. That is
  conventional for a localhost development default and it is not a real secret, but anything
  genuinely sensitive belongs in user-secrets or a secret store, not in the repository.
- **No pagination.** `GET /warehouse` and the items list return everything.
- **No optimistic concurrency.** Two clients updating the same warehouse: last write wins,
  silently.
- **Deleting a warehouse uses `ExecuteDelete`** and leans on the database's cascade rather than
  loading the aggregate. Efficient, but it bypasses the domain — if removing a warehouse ever
  needed to *do* something, this would have to change.
- **The clock is read inside the domain** (`DateTimeOffset.UtcNow`), which makes timestamps
  awkward to assert on. `TimeProvider` would fix it.
- **Integration tests need the compose SQL Server running** (see below).
- **`compose.yaml` still publishes `4443:8081`**, left from the template. Nothing listens on
  8081 now that the service is HTTP-only, so the mapping is dead weight.

### What I would do next, in order

1. **Authentication and authorisation** — JWT bearer, `[Authorize]` on writes, a role policy so
   only a warehouse manager can delete. Deliberately without a user store or refresh tokens;
   the point is to show the wiring, including the OpenAPI security scheme so Swagger UI's
   Authorize button works.
2. **Optimistic concurrency** — a `rowversion` token, `If-Match`/`ETag`, `409` on a stale write.
3. **Pagination** on both list endpoints, with a total count.
4. **`/health`** via `AddHealthChecks().AddDbContextCheck()`, wired into the compose healthcheck.
5. **Stock movements as first-class events** rather than a mutable quantity, if the domain
   warranted it — an audit trail of what moved, when and why, with the quantity projected from it.

## Testing

29 tests split by what they are actually testing.

**Unit tests on the aggregate** (`WarehouseAggregateTests`, 7 of them) — no database, no host, no mapper.
That the invariants can be tested this way is the main practical payoff of the refactor:
duplicate SKUs, case-insensitive matching, the deactivated-warehouse rule, SKU reuse after
removal, and the negative-quantity guard.

**Integration tests** (`WarehouseApiTests`, `ItemApiTests`, 22 of them) — the real application via
`WebApplicationFactory`, over HTTP, against real SQL Server. They cover the status codes and
`Location` headers, the ProblemDetails shapes including nested `Address.Street` paths, that
`Code` and `CreatedAt` survive an update trying to overwrite them, cascade delete, parent
scoping (an item id is invisible through the wrong warehouse), and `IsOnStock` following
quantity down to zero and back up.

**Why real SQL Server and not SQLite or the in-memory provider:** the two most interesting
pieces of behaviour — the computed column and the composite unique index — do not exist outside
SQL Server. Testing them against a different engine would prove nothing.

**Why not Testcontainers:** `Testcontainers.MsSql` defaults to
`mcr.microsoft.com/mssql/server`, which has no arm64 image, and pointing it at
`azure-sql-edge` (which does) breaks its readiness check, because that image ships no `sqlcmd`.
Instead each run creates a uniquely named database on the SQL Server compose already provides
and drops it afterwards. The cost is a documented prerequisite; on an x64 CI runner
Testcontainers would be the better answer.

No assertion library. FluentAssertions moved to a commercial licence at version 8, so plain
`Assert` it is.

## How I used AI, and how I checked it

I built this with Claude Code (Claude Opus) as the primary author, working in a tight
loop: I described the intent, it wrote the code, and then I ran it. Roughly every line here
was AI-written; the engineering was in specifying, reviewing, and refusing what did not hold up.

**Verification was always execution, never inspection alone.** Each slice was checked against a
running database before moving on — `curl` against every endpoint for each status code, reading
the SQL EF actually emitted, and reading generated migrations rather than assuming them.

Four things AI got wrong, and what caught them:

1. **`ItemCount` looked right and was quietly wrong.** Mapped as `source.Items.Count` — the
   property — EF emitted a `LEFT JOIN` that dragged back every column of every item and counted
   in memory. The returned numbers were correct, so no test would have failed. Reading the
   generated SQL in the EF logs caught it; `source.Items.Count()`, the extension method,
   compiles to a `COUNT(*)` subquery. This is the clearest case for verifying behaviour rather
   than output.
2. **A stale build hid a broken migration, twice.** `dotnet ef migrations add` writes files
   *after* it builds, so `dotnet run --no-build` ran a binary with no migrations in it: EF
   created an empty database and the seeder died on a missing table. Only running it surfaced
   this; the build was green both times.
3. **`dotnet add package` silently bumped an unrelated dependency**, moving
   `Microsoft.AspNetCore.OpenApi` from 10.0.8 to 10.0.12. Caught by reading the restore output
   instead of trusting it. It happened to resolve a high-severity advisory in a transitive
   `Microsoft.OpenApi`, but it was not an asked-for change.
4. **Confidently wrong about a library version.** The model's knowledge of Mapster stopped at
   7.x while NuGet resolved 10.0.12; the API surface was verified against the actual assembly
   before any code was written against it.

**I also checked that the tests could fail.** After the suite went green I deleted the
deactivated-warehouse invariant from the aggregate and re-ran: exactly two tests failed, the
unit test and the integration test covering that rule. Then I restored it. A green suite that
has never been seen to fail is not evidence.
